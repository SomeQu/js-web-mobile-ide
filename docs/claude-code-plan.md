# План реализации для Claude Code — Мобильная JS/TS IDE

Документ рассчитан на то, чтобы скармливать его по частям Claude Code (или держать как `CLAUDE.md`/roadmap в корне репозитория). Каждая фаза — это отдельная сессия работы с агентом: у неё есть чёткая цель, набор файлов на выходе и критерий "готово".

---

## 0. Подготовка репозитория (сделать вручную, до Claude Code)

1. Создать монорепо: `pnpm` + `pnpm workspaces` (легче для WASM-зависимостей, чем npm/yarn classic).
2. Структура:
   ```
   /packages
     /vfs
     /resolver
     /registry-client
     /bundler
     /node-shims
     /runtime-bridge
     /git-client
     /ai-assistant
     /editor-core
   /apps
     /ios
   /docs
     architecture.md
     claude-code-plan.md   (этот файл)
   ```
3. Корневой `CLAUDE.md` с правилами для агента (см. раздел 8).
4. TypeScript project references между пакетами (`tsconfig.json` с `references`), чтобы границы были видны компилятору, а не только на словах.

**Что попросить у Claude Code в первой сессии:** инициализировать монорепо, настроить pnpm workspaces, base tsconfig, ESLint/Prettier, пустые пакеты с `package.json` и `index.ts`-заглушками по структуре выше.

## 1. Фаза 1 — `vfs` (виртуальная файловая система)

**Цель:** независимый от UI и платформы модуль, эмулирующий POSIX-подобную ФС в памяти/на диске песочницы, без реальных симлинков.

**Задачи для Claude Code:**
- Интерфейс `IVirtualFileSystem`: `readFile`, `writeFile`, `readdir`, `stat`, `mkdir`, `unlink`, `rename`.
- Реализация поверх обычного объекта в памяти (для юнит-тестов) + отдельная реализация поверх файловой системы Node (для локальной разработки/CI, до появления iOS-обёртки).
- Поддержка "виртуальных ссылок" (эмуляция симлинков без реальных OS-примитивов) — нужно для будущей PnP-подобной схемы.
- Юнит-тесты: создание/чтение/удаление файлов, вложенные директории, edge-кейсы путей (`../`, абсолютные/относительные).

**Критерий готовности:** 100% тестового покрытия базовых операций, пакет собирается и импортируется независимо, нет ни одной зависимости на UI/React Native/Swift.

**Промпт для Claude Code (пример):**
> В пакете `packages/vfs` реализуй `IVirtualFileSystem` согласно интерфейсу в `docs/architecture.md` разделу 3.3. Добавь in-memory реализацию и тесты на Vitest. Не используй Node-специфичные API (`fs`, `path` из node) — только чистый TS, чтобы пакет мог работать в JavaScriptCore.

## 2. Фаза 2 — `editor-core`

**Цель:** обвязка над Monaco или CodeMirror, независимая от остальной системы — получает текст файла, отдаёт изменения.

**Задачи:**
- Прототип на обоих редакторах (Monaco и CodeMirror) в виде минимального HTML-демо.
- Сравнение по: размер бандла, скорость инициализации, потребление памяти на слабом устройстве (эмулировать throttling в Chrome DevTools).
- Интерфейс `IEditor`: `open(path, content)`, `onChange(callback)`, `setLanguage`, `getSelection`.
- Подключение TS Language Server (для автодополнения) — тут отдельно проверить, насколько тяжело тащить `typescript` в бандл для мобильного WebView.

**Критерий готовности:** решение зафиксировано (Monaco или CodeMirror) с обоснованием в `docs/`, демо открывает/редактирует файл через `IEditor`, не зная про vfs/resolver напрямую.

## 3. Фаза 3 — `resolver` + `registry-client`

**Цель:** по `package.json` + lock-файлу построить граф зависимостей и скачать пакеты.

**Задачи:**
- `registry-client`: HTTP-клиент к npm registry (метаданные пакета, скачивание `.tgz`, распаковка через чистую JS gzip/tar-библиотеку).
- `resolver`: алгоритм semver-резолвинга, дедупликация версий, построение дерева/графа модулей.
- Черновой список поддерживаемых lock-форматов на старте: `package-lock.json` (npm) — первым, `yarn.lock` и `pnpm-lock.yaml` — позже.
- Кэш скачанных `.tgz` по имени+версии через `vfs`.
- Тесты на реальных небольших пакетах (`lodash`, `react`) — сначала через мок registry-ответов, потом live-тест с настоящим npm registry.

**Критерий готовности:** для тестового `package.json` с 3-5 зависимостями пакет строит корректное дерево и раскладывает файлы во `vfs`, без обращения к Node-специфичным API.

---

## 4. Фаза 4 — `bundler` (esbuild-wasm/swc-wasm)

**Цель:** собрать JSX/TS-проект из файлов во `vfs` в исполняемый бандл.

**Задачи:**
- Интеграция esbuild-wasm с кастомным `resolve`/`load`-плагином, который ходит не в реальную ФС, а в `vfs`.
- Инкрементальная пересборка (watch-режим на изменения файлов).
- Замер производительности на объёме ~50 файлов/10 зависимостей — с прицелом на будущий мобильный чип.

**Критерий готовности:** "Hello React" (App.tsx + пара компонентов + импорт из React, полученного через `resolver`) собирается в единый JS-бандл без обращения к настоящему Node.

---

## 5. Фаза 5 — `node-shims`

**Цель:** минимальный набор полифиллов, достаточный для типового дев-тулинга фронтенд-пакетов.

**Задачи:**
- Взять за основу существующие браузерные полифиллы (`node-stdlib-browser` и аналоги), адаптировать под `vfs` вместо реальной ФС.
- Список приоритетных модулей: `path`, `process` (частично), `buffer`, `events`. `fs`/`net`/`child_process` — заглушки с понятной ошибкой вместо тихого падения.
- "Чёрный список" — детектор пакетов с `postinstall`, использующих `node-gyp`/`prebuild-install`, с понятным сообщением пользователю до попытки сборки.

**Критерий готовности:** 5-10 популярных фронтенд-библиотек (React, Vue, Zustand, date-fns, clsx) собираются и работают через bundler без ошибок про отсутствующие модули.

---

## 6. Фаза 6 — `runtime-bridge` + iOS-обвязка

**Цель:** связать всё вышеперечисленное с нативным iOS-приложением.

**Задачи:**
- Swift-таргет `apps/ios`, встраивающий WKWebView, куда грузится собранный бандл пакетов (vfs+resolver+bundler+editor-core).
- Мост вызовов Swift ↔ JS: `evaluateJavaScript` (Swift→JS) и `WKScriptMessageHandler` (JS→Swift).
- Live preview: второй WKWebView + Service Worker, перехватывающий fetch-запросы и отвечающий из vfs.
- Базовый файловый менеджер в SwiftUI, использующий мост к `vfs`.

**Критерий готовности:** можно открыть проект (несколько файлов, включая один npm-пакет), увидеть live-preview результата в WKWebView, изменения в редакторе долетают до preview.

*Эта фаза, скорее всего, ведётся не только Claude Code (нужен Xcode/симулятор) — агент может генерировать Swift-код и JS-обвязку, но сборка/тестирование на устройстве — вручную.*

---

## 7. Фаза 7 — `git-client`

**Цель:** git-операции (clone/commit/push/pull) без настоящего git-бинарника.

**Задачи:**
- Интеграция isomorphic-git поверх `vfs`.
- UI для базовых операций: статус, diff, commit, push/pull с аутентификацией (токен/SSH-ключ — уточнить, как хранить секреты в iOS Keychain через мост).

**Критерий готовности:** clone публичного репозитория, правка файла, commit + push проходят end-to-end.

---

## 8. Фаза 8 — `ai-assistant`

**Цель:** чат-ассистент с tool-use поверх Anthropic Messages API.

**Задачи:**
- HTTP-клиент к `/v1/messages` (стриминг ответов).
- Набор tool-функций: `read_file`/`write_file`/`apply_diff` (через `vfs`), `search_codebase`, `get_open_file`/`get_selection` (через `editor-core`).
- System-промпт с контекстом проекта (дерево файлов, открытый файл).
- UI: боковая панель чата + diff-view для принятия/отклонения правок.

**Критерий готовности:** ассистент может прочитать файл, предложить правку, пользователь принимает — правка применяется через `vfs`, редактор обновляется.

## 9. `CLAUDE.md` — правила для агента в проекте (положить в корень репо)

```markdown
# Правила для Claude Code в этом репозитории

- Монорепо на pnpm workspaces. Каждый пакет в /packages должен собираться и тестироваться независимо.
- Никаких Node-специфичных API (fs, net, child_process из 'node:...') внутри /packages, кроме тестовых окружений (файлы *.test.ts). Итоговый рантайм — JavaScriptCore/WKWebView, а не Node.
- Общение между пакетами — только через экспортируемые интерфейсы из index.ts, не через прямые импорты внутренних файлов другого пакета.
- Каждая новая фича — сначала тест, потом реализация (TDD там, где это применимо к чистой логике: vfs, resolver, node-shims).
- Перед добавлением новой npm-зависимости в сам инструмент — проверить, что она не тянет нативные биндинги (node-gyp).
- Соглашение по коммитам: Conventional Commits (feat/fix/chore/docs).
```

## 10. Как вести сессии с Claude Code практически

- Одна фаза = одна (или несколько) сессия. Не пытаться просить агента "сделай всё сразу" — границы фаз специально сделаны маленькими и тестируемыми.
- В начале сессии — указывать Claude Code путь к этому файлу и текущий номер фазы, плюс `docs/architecture.md` для контекста интерфейсов.
- После каждой фазы — просить агента написать краткий `docs/decisions/00X-<фаза>.md` с тем, какие решения были приняты и почему (особенно если пришлось отклониться от плана) — это ваш "журнал архитектурных решений" (ADR), полезно через месяцы, когда будете это же самое объяснять новому разработчику или Claude Code в новой сессии без полного контекста.
